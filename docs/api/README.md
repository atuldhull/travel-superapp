# API specification

> Installed by prompt `[IV.18.19.10]`. Updated by `[P3]` of the Documentation 8.5→10 series — now ships a hosted viewer + GH Pages publish pipeline. Companion to [`docs/onboarding.md`](../onboarding.md) + [`apps/api/scripts/export-openapi.ts`](../../apps/api/scripts/export-openapi.ts).

## Files

| File                 | What                                                                                                                                                                  |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `openapi.yaml`       | Generated OpenAPI 3 spec. Source of truth. Committed so consumers (SDK gen, mobile bindings, third-party integrators) have a stable artifact without booting the api. |
| `index.html`         | **Thin Redoc viewer** (~1 KB). Opens `openapi.yaml` at page-load via the Redoc CDN. Never drifts from the YAML — regenerating the YAML is enough.                     |
| `index.bundled.html` | **Offline-capable viewer** (~1.8 MB). Single file with Redoc + the spec inlined. Generated by `pnpm docs:api:build`. Gitignored — derived artifact.                   |

## Browse it

| Where        | Open                                                                                                                                                                                                                |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Locally**  | `docs/api/index.html` — open it directly in any browser. Loads the YAML next to it.                                                                                                                                 |
| **Offline**  | Run `pnpm docs:api:build` once, then open `docs/api/index.bundled.html`. Works on a plane.                                                                                                                          |
| **Hosted**   | `https://<owner>.github.io/<repo>/` — published by [.github/workflows/docs-api.yml](../../.github/workflows/docs-api.yml) on every push to `main` that changes the spec. Operator-owed setup below.                 |
| **Live API** | The running api also serves the YAML at `/api/v1/openapi.yaml` and a Swagger UI at `/api/v1/docs` (NestJS `SwaggerModule.setup`). The committed YAML matches what that endpoint returns at the SHA on which it ran. |

## Regenerate the spec

```sh
pnpm --filter=api api:openapi
```

The script boots `AppModule` in-process, walks Nest's controller + route metadata via `@nestjs/swagger`'s `SwaggerModule.createDocument`, and writes `openapi.yaml` here. No HTTP server starts — pure metadata export.

The drift gate (`pnpm sdk:check`) already fails CI when this YAML is stale relative to the controllers — no need to remember to regenerate, just run `pnpm sdk:check` before pushing.

## Regenerate the offline viewer

```sh
pnpm docs:api:build      # writes docs/api/index.bundled.html (~1.8 MB)
```

Uses `@redocly/cli build-docs` under the hood. No install required — `npx -y` pulls it on demand. The output is a single self-contained HTML page (no CDN dependency).

`@ApiBody` / `@ApiResponse` rollout is intentionally per-module instead of a single mega-PR — each module owner adds them when they next touch their module. The drift gate already prevents the spec from rotting; richness is incremental.

## Operator-owed (enable hosted viewer)

One-time setup in repo **Settings → Pages**:

1. **Source** → "GitHub Actions".
2. Push to `main` (or run [docs-api](../../.github/workflows/docs-api.yml) via "Run workflow") — the workflow builds + deploys.
3. The page comes up at `https://<owner>.github.io/<repo>/`.

Until step 1 is done, the workflow's build step still runs as PR smoke; only the deploy step needs Pages to be on.

## Why YAML over JSON

Diffs are readable. A reviewer skimming a PR can spot "added GET /foo/bar" or "removed `?limit=` query param" in YAML; the JSON variant is one giant escaped blob. Both formats are equivalent — import-side tooling reads either.
