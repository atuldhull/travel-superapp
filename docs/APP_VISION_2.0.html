TravelSuperApp 2.0 — agentic + social

1.0 is a complete, env-gated backend with a clumsy face. 2.0 is not "more features" — it is one thesis: an agent that travels with you, and a network that makes every agent smarter. This is the blueprint and the drop-in prompt book to build it without a rewrite.

1 · The 2.0 thesis

Agentic and social only look like two upgrades. Wired together they are a single flywheel where each side feeds the other. That coupling — not either feature alone — is the entire 2.0.

The agent makes content

It watched your flight, re-planned when the museum closed, you actually went. That is authentic lived trip data — the one thing every social travel app fails to get. Everyone else has stale influencer junk.

The network grounds the agent

What real travelers did when plans broke, which itineraries performed, who you trust. That is RAG over outcomes, not marketing copy. pgvector is already in Postgres for exactly this.

Memory Books are the join

The agent auto-drafts one from the trip it ran; you publish; its embedding indexes into discovery and becomes context for the next person's agent. The artifact already exists in 1.0.

The one sentence
Agent run → auto-drafted Memory Book → publish → embedded → grounds the next agent. Everything else in this document is plumbing for that loop. If a 2.0 task does not eventually serve this sentence, defer it.

3 · The flywheel

The single diagram that matters. Each arrow is cheap because the node it points at already exists in 1.0.

The 2.0 loop
  1. You create a trip (1.0 surface, unchanged) /trips/new → POST /trips → AI plan via existing 4-tier chain
  2. The agent attaches and watches Subscribes to weather + flight + your edits. Free signal adapters. Ships dark behind a flag.
  3. Something changes → the agent re-plans Museum closed / storm / flight delay → it drafts a new day, asks you to confirm (never auto-spends).
  4. The trip ends → the agent auto-drafts a Memory Book It already knows what you did and what changed. The Memory Book artifact exists in 1.0 — it fills it in.
  5. You publish (default private; you opt in) Memory Book → public artifact on the existing /featured + a new feed. Privacy-fenced.
  6. The published trip is embedded into pgvector Becomes (a) discovery — "trips like this", (b) grounding context for the next traveler's agent.
  7. Someone else's agent retrieves your real outcome Their re-plan is now grounded in what actually happened, not generic LLM guesswork. Loop closes.
Why the coupling is the moat
A pure travel agent is a thin wrapper over an LLM — anyone ships that in a weekend. A pure social travel app has a cold-start content problem nobody solves. Fused, the agent solves the network's content problem and the network solves the agent's grounding problem. The data accrues; the wrapper does not.

4 · Why this is not a rewrite (and the one hard scope cut)

The biggest risk in any "2.0" is that "upgrade" silently means "rebuild". Here is what explicitly stays, what is added, and the one capability we deliberately do not build.

Stays exactly as-isno churn
  • All 17 api modules, hex boundaries, Prisma schema (append-only)
  • The 4-tier AI chain + every existing adapter
  • Auth, payments scaffold, safety, admin, observability
  • All 58 web pages (they get the agent/feed added, not replaced)
Added (new surfaces)net-new
  • modules/agent — event-driven loop + tool registry
  • Graph + feed extensions to social/feed
  • Discovery service (pgvector over trip embeddings)
  • ~3 free signal adapters + ~5 append-only Prisma tables
The one hard cut — read carefully
Stripe is stub mode (you're a student; live keys blocked) and the project's durable rule is no paid external sources. Therefore the agent does not autonomously spend money or make real bookings. "Acts" = re-plans, notifies, and drafts a booking for you to confirm. This is also the safer product: an agent that books a non-refundable hotel on a bad signal is a lawsuit, not a feature. Human-in-the-loop is the design, not a limitation.

5 · Track A — from planner to agent

1.0's trip planner is a function: prompt in, itinerary out, done. A 2.0 agent is a process: it persists, subscribes to the world, and acts over the life of the trip.

Dimension 1.0 planner 2.0 agent
LifetimeOne requestTrip start → trip end
TriggerUser clicks "Generate"World events: weather, flight, geofence, user edit, cron tick
MemoryNone (stateless)Append-only run log + episodic pgvector recall
OutputProse itineraryA proposed diff to the plan + a notification + a draft Memory Book
Authorityn/aPropose-and-confirm. Never autonomous spend.
Design stance
Keep the LLM on the edges (summarise the change, draft the new day, write the Memory Book) and keep the loop deterministic (poll → diff → decide → enqueue). On the free tier (Gemini Flash / Ollama qwen2.5:7b) long autonomous tool-use is unreliable — a short deterministic loop with LLM leaf-calls is robust where a "let the LLM drive everything" agent is not.

6 · The agent loop architecture

A new modules/agent following the exact hex pattern of every other module. The loop is a small state machine; the LLM is one tool among several.

modules/agent/ ├── domain/ │ ├── agent-run.entity.ts ← aggregate: status, plan-version, step log │ ├── trip-watch.entity.ts ← what signals this run subscribes to │ └── plan-diff.vo.ts ← a proposed change (add/move/drop a stop) ├── application/ │ ├── ports/ │ │ ├── signal-source.port.ts ← weather | flight | transit | geofence │ │ ├── agent-memory.port.ts ← episodic recall (pgvector) │ │ └── plan-tool.port.ts ← wraps the existing 1.0 trip-planner │ ├── start-trip-watch.use-case.ts │ ├── evaluate-signals.use-case.ts ← the deterministic core: poll → diff → decide │ ├── propose-replan.use-case.ts ← LLM leaf-call: draft the new day + summary │ └── confirm-replan.use-case.ts ← user accepted → apply diff to trip ├── infrastructure/ │ ├── open-meteo-weather.adapter.ts ← FREE, no key │ ├── opensky-flight.adapter.ts ← FREE, anonymous tier │ ├── stub-signal.adapter.ts ← always present (env-gated default) │ └── pgvector-agent-memory.adapter.ts └── interface/ ├── agent.controller.ts ← REST: status, accept/decline a proposal └── agent.scheduler.ts ← cron tick drives evaluate-signals
One tick of the loop (deterministic core)
  1. Scheduler firesReuses existing cron infra; one tick per active trip-watch.
  2. Pull signalsEach signal-source.port adapter returns a typed snapshot (weather, flight state).
  3. Diff against last snapshotPure function. No LLM. "Rain 80% on the day you planned the rooftop walk."
  4. Decision gateThreshold rules decide if the change is material. Below threshold → log + sleep.
  5. LLM leaf-call (only if material)propose-replan calls the 1.0 planner tool to draft a swapped day + a one-line "why".
  6. Enqueue a proposal, not an actionWrites a plan-diff + pushes a notification via the existing notifications module.
  7. User confirms (or auto-applies trivial)Confirm → apply diff to the trip. Decline → record, raise threshold.

8 · Agent state & memory

An agent needs durable state. Three stores, each one the project already runs — nothing new to operate.

Postgres — run log

agent_run + agent_step, append-only (honors the Prisma append-only constraint). Full audit of every signal seen and every proposal made.

Redis — live loop

Last-snapshot cache + per-watch lock so two scheduler ticks can't double-propose. Reuses the existing Redis 7 instance.

pgvector — episodic

Embeddings of "what happened when plans changed" — the agent recalls similar past situations and retrieves grounded outcomes from the social network (§17).

Schema rule reminder
CLAUDE.md hard-constraint #8: Prisma schema is append-only unless a prompt explicitly permits edits. Every 2.0 table is additive — new models, no column drops, no destructive migrations. Each POST-2.0 prompt that touches the schema states this explicitly.

9 · The "acts" boundary — what the agent may and may not do

The single most important product decision in Track A. Get this wrong and the agent is a liability; get it right and it is trustworthy.

ActionAuthorityWhy
Re-order / swap stops within the existing plan auto, reversible Cheap, undoable, low-stakes. Notify after.
Surface a weather/closure warning auto Pure information; never harmful.
Propose a materially different day propose → confirm Changes the trip shape; user owns the call.
Draft a Memory Book draft → user publishes It's the user's story; they edit and decide to share.
Spend money / confirm a booking never (2.0) Stripe stubbed + durable no-paid rule + liability. Agent prepares; human commits.
Trust UX
Every autonomous action gets an undo affordance and a one-line "why I did this". Every proposal shows the signal that triggered it. The agent's credibility is the product — surface its reasoning, never hide it.

11 · Track B — from hearts to a network

1.0 already has a social module (hearts, votes, reviews, karma, public profiles) and a feed module. Track B is not greenfield — it is a graph + a feed + a publishing model layered on top of what exists.

1.0 social2.0 network
Anonymous hearts on shared tripsIdentified reactions tied to a follow graph
Public profile = bare list of reviewsCreator profile = published trips + Memory Books + followers
No relationship between usersFollow graph → personalised feed + discovery signal
Content = whatever users manually shareContent = agent-drafted, real, lived trips (the flywheel)
Sequencing insight
Do not build the network before the agent. Without the agent, the network has the same cold-start content problem as every competitor. Build Track A first so that when the network opens, it opens onto real, auto-generated content. Phase order in §20 reflects this.

12 · The follow graph

The smallest graph that works. Resist building Twitter. At zero scale, simple beats clever.

// additive Prisma models (append-only) model Follow { followerId String followeeId String createdAt DateTime @default(now()) @@id([followerId, followeeId]) @@index([followeeId]) // "who follows X" } model TripPublication { id String @id @default(cuid()) tripId String @unique authorId String memoryBookId String? // the agent-drafted artifact visibility Visibility // PRIVATE | FOLLOWERS | PUBLIC publishedAt DateTime? embedding Unsupported("vector(1024)")? // pgvector, §15 (1024 = PlaceEmbedding precedent) }
Why a join table, not arrays
Follow as a composite-key table indexes both directions and stays correct under concurrency. No follower-count denormalisation in 2.0 — compute it; optimise only if a real dashboard says to.

13 · The feed

The single place teams over-engineer. At your scale the correct architecture is the boring one.

Phase B: pull / fan-out-on-readcorrect now

On feed load: query TripPublication where author ∈ (who I follow) ∪ public, order by recency, paginate. One indexed query. Zero precompute. Correct until tens of thousands of DAU.

Later: fan-out-on-writeonly if needed

Precomputed per-user timeline in Redis. Only when read latency on the pull query is measured to be a problem. Premature here = wasted weeks.

Ranking
v1 feed = reverse-chronological. No engagement ranking. It is honest, debuggable, and removes a whole ML surface from the critical path. Add pgvector "similar to trips you saved" as a separate discovery rail (§15), not as feed ranking.

14 · Publishing model

Travel content is uniquely sensitive: it broadcasts that your home is empty and where you physically are. The publishing model is a safety feature, not a sharing convenience.

Publish flow (privacy-fenced by default)
  1. Default = PRIVATEEvery trip and agent-drafted Memory Book starts private. No accidental broadcast.
  2. Publish is opt-in and trip-end-gatedYou cannot publish a live, in-progress trip's location. Publish unlocks after the trip's end date.
  3. Location fuzzing on publicPUBLIC visibility coarsens precise geo (city-level), keeps it exact for FOLLOWERS if the user allows.
  4. Followers vs public splitThree-state Visibility enum lets the cautious share with a trusted circle only.
  5. Unpublish is instant + de-indexesSets visibility PRIVATE and removes the embedding from discovery in the same transaction.
Non-negotiable
No code path may publish a trip whose end date is in the future. This intersects modules/safety and must be enforced in the domain layer (a TripPublication invariant), not just the UI.

15 · Discovery (pgvector — the part 1.0 pre-provisioned)

pgvector has been in Postgres since 1.0 with nothing using it. Discovery is where it finally earns its place.

Discovery pipeline
  1. On publish, embed the tripDestination + vibe + the agent's narrative → embedding via the already-running local Ollama (mxbai-embed-large, free, $0).
  2. Store on TripPublication.embeddingvector(1024), ivfflat vector_l2_ops lists=100 — matches the existing PlaceEmbedding. No new datastore.
  3. "Trips like this" railCosine-nearest published trips, filtered by visibility the viewer may see.
  4. Feeds back into the agent (§17)Same index is the agent's grounding retrieval. One embedding, two consumers.
Embedding model — free path
Use the already-running local Ollama (model mxbai-embed-large, 1024-dim) via native fetch so embeddings cost $0 and need no external key — consistent with the durable no-paid-source rule. Verified: apps/ai-service is a README only (no Python service) — do not stand one up. Gemini's embedding endpoint is the env-gated upgrade if quality demands it later.

16 · Privacy & safety model

The features that make a travel network trustworthy. Treat these as acceptance criteria, not nice-to-haves.

  • Private by default — every new artifact; sharing is always an explicit action.
  • No live-location publishing — enforced as a domain invariant (§14).
  • Geo coarsening on PUBLIC — exact coordinates never leave the followers tier without opt-in.
  • Block / mute — a blocked user cannot see, follow, or react; reuses moderation patterns from modules/admin.
  • De-index on unpublish — embedding removal is in the same transaction as the visibility flip; no ghost in discovery.
  • Report → existing moderation — published trips flow into the 1.0 scam/abuse report + admin triage surfaces, not a new pipeline.
Decision needed
Is the default sharing tier FOLLOWERS or PUBLIC when a user does choose to publish? Recommendation: FOLLOWERS first; PUBLIC requires a second explicit confirm. Errs toward safety for a travel dataset. Logged in §22.

17 · Where A meets B (the actual 2.0 moment)

Tracks A and B are individually useful but ordinary. These two seams are what make the product a 2.0 rather than two bolt-ons.

Seam 1 · Agent → content

When a trip-watch closes, confirm-replan's sibling use-case draft-memory-book fires: it composes the real itinerary + what changed + the user's photos (1.0 media variants) into a Memory Book draft. The network's content problem is solved by a byproduct of Track A.

Seam 2 · Network → grounding

propose-replan queries the pgvector index for published, real outcomes near this destination/situation and injects the top-k as grounding into the LLM leaf-call. The agent's quality problem is solved by a byproduct of Track B.

Build-order consequence
Seam 1 needs Track A done. Seam 2 needs Track B done. That is exactly why §20 sequences A → B → (A∩B). Phase C is small precisely because A and B already exist when you reach it.

20 · Phase A / B / C sequencing

You are on a tight timeline and the workflow rule is small, sequential, confirmed slices. This is the honest order — and why Phase C is cheap.

Phase A — ships dark, zero front-end change
Agent core

modules/agent + signal ports + Open-Meteo/OpenSky/stub adapters + deterministic loop + propose/confirm + append-only run log. Notify via existing notifications module. Behind a feature flag — no UI risk. Self-contained and demoable on its own.

Phase B — extends existing social/feed modules
Social substrate

Follow + TripPublication + UserBlock + pull feed + privacy-fenced publish + creator profile. Extends modules/social/feed; does not touch Phase A.

Phase C — the 2.0 moment, small because A+B exist
The fusion

Seam 1 (draft-memory-book on trip-watch close) + Seam 2 (pgvector grounding injected into propose-replan) + the "trips like this" discovery rail. ~3 prompts, because every dependency already shipped.

If you only ship one phase
Ship Phase A. A travel agent that watches your trip and re-plans for free is a complete, demoable product on its own. Phase B without A is just another social app; Phase C without both is nothing. A is the keystone.
